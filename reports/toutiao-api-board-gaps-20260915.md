## Source-built-host follow-up and OH direct-link fix

The captured IME host above did not request `ohos.permission.GET_NETWORK_INFO`; root also could not use the OH NetConn service. A separately **source-built** and installed `org.westlake.sourcehost` HAP requested both `GET_NETWORK_INFO` and `INTERNET` and had granted states `[0,0]` (`0` is granted in the inspected OH bundle source). Its installed HAP SHA-256 `fea4e312ce3e29e297ac0aad3f2c13c29bb3f18a50ff034f0c1ae0cb7c291503` matched `source-closure/verify/out/source-window-host-connectivity-signed1/source-host.hap`. This gives a controlled caller for the real OH service without relabelling the captured IME host as source-built.

Under that source host, the prior helper (SHA-256 `c0cfb72f861be7f1ca880c3d54d7cf1eda296c224be9c033b76def728bf0b5b6`) reached `backend=oh-netconn`, netId 100, `wlan0`, and successful OH statuses, but the initial Android-facing snapshot had MTU 0 and 0/0/0 address/DNS/route counts. The same-PID inspection nevertheless found a complete view tree with 13 feed items behind the privacy dialog. Its isolated app report is `source-closure/verify/out/toutiao-api-shim-fixes-sourcehost-device49/device-report.json`; `source_ui_accepted=false` and `full_source_closure=false`.

The generic Westlake JNI fix merged as [westlake PR #3](https://github.com/a2hlab/westlake/pull/3), merge commit `cf73b436887e5ebba4ea69dac0a1dfa734d44997`. It supplements incomplete direct-OH link properties using the process-observed kernel routes **only when** the OH interface and observed route interface exactly match. It keeps the real OH handle, capabilities and metering. The rebuilt helper SHA-256 was `091fc804ffa6985f3e47ab05359892c56442e9ab1d70945a5e1ca6c7870aa491`, matching the live app child's helper hash. The framework staging report (`source-closure/verify/out/framework-oh-direct-links-device52/device-report.json`) SHA-256 `2ce6b5b0a7bd482e922af9ff422b23676f28253b3ce45197c156c6b7956fa484` reports `passed=true`, `full_stack_accepted=false`.

The new source-host app report (`source-closure/verify/out/toutiao-oh-direct-links-sourcehost-device53/device-report.json`) SHA-256 `eefe6d2fc97e096a8836a060abc6e172f33981d63be417a8480dd4fc7f8f3dc3` used the same unchanged APK SHA-256 `a1112a0c941f865847c2fab9138cf815735268fbfcd41d697412fb80992c7395`. Its child UID 20010056 showed `self_network_info=1`, OH status `rc=0/0/0/0/0`, real netId 100 on `wlan0`, MTU 1500, and 2/2/2 usable address/DNS/route counts. It registered `requestNetwork` (`TRACK_DEFAULT`, requestId 1) and `listenForNetwork` (`LISTEN`, requestId 2), and delivered an available callback for requestId 1/netId 100. The settled same-PID view tree (`source-closure/verify/out/toutiao-oh-direct-links-sourcehost-device53-inspection3/view-tree.txt`) SHA-256 `eaafa9f949f52439734deb6fa568d61e92537796c6cf46c4d4dbb8b2816ac250` had 13 feed items and two fetched image drawables behind the still-open privacy dialog. The exact child/parent PIDs 12615/12594 were stopped after inspection by UID and executable inode. This is direct-OH link evidence; it does not prove the uncached fallback path, callback loss/reconnect, configured proxy, consent/input acceptance, or full source closure. The two source-host launches occurred at different board epochs, so their timing is not a controlled performance A/B.

## Remaining API gaps and proof needed

| Boundary | Current finding | Next decisive probe |
| --- | --- | --- |
| OH network identity | Source-built host with `GET_NETWORK_INFO` grant reached the real OH direct default netId 100, `wlan0`, and 2/2/2 usable links after reconciliation. Captured IME host/root still returned 201; the `oh-uncached+kernel-links` fallback was not reached. | Probe the uncached path with a caller whose direct default call fails while listed OH properties/capabilities work; require a fresh promotion log and matching routed interface. |
| Connectivity callbacks | Both hosts reached request/listen registrations and one available callback; the source host delivered it for real netId 100. No timeout, `CALLBACK_UNAVAIL`, loss/reconnect, release, or requestId 2 outcome observed. | Exercise controlled loss/reconnect, unsatisfiable request/timeout and release, comparing callback order and request identity with the unchanged Android reference. |

| Media/shortcut service | Local binder lookup passed at startup; lifecycle and persistent service semantics were not probed. | Binder identity, callbacks and lifecycle behavior under app feature use. |
| Java API scan | Zero directly referenced missing methods/fields; 11 absent classes had zero references. There are 424 hollow-method candidates and 32 existence probes. | Promote individual items only after a reached call and wrong behavior; use feature paths and computed-reflection evidence. |
| Native API queue | The 324 registered/1,620 not-observed result belongs to the prior exact runtime lock and helper hash; the direct-link helper changes that lock. | Re-lock and trace the current runtime, add classloader-aware final JNI lookup, library-load/build-ID, invocation and computed-reflection events, then exercise more features. `not-observed` cannot be called missing. |
